# Management workspace design

Prepared 15 October 2026 on `design/management-ui`, based on the deployed customer
redesign and staff-account integration at `b899140`.

## Scope

This change presents the existing `/management/` functionality as a blue/navy
staff workspace. It adds permission-filtered navigation, overview record cards,
record-area shortcuts, personal audit activity, styled lists/forms, service status
badges, and a matching staff login. The counts come from the existing permitted
querysets; there are no invented infrastructure metrics or revenue charts.

Navigation collapses into wrapping links on phones. Wide record tables retain
horizontal scrolling inside their existing table containers.

The existing AdminSite, ModelAdmins, URLs, permissions, CSRF, staff cookies,
search/filter/pagination, staff creation, validation, and audit behavior remain
authoritative. Financial lifecycle records remain read-only. Existing confirmed
status reconciliation remains the only Management remote workflow; no new power,
payment, provisioning, deletion, refund or suspension action is introduced.

## Implementation

- `templates/admin/base_site.html` extends the bundled template of the same name.
  Django skips the current origin when resolving the parent, preventing recursion.
  Overrides are conditional on `management_ui`; the legacy admin falls back to
  its bundled presentation. Customer templates do not use this base.
- `cloud_portal/settings.py` adds `BASE_DIR / 'templates'` to the template search
  directories. Other deployment and database settings are unchanged.
- `ManagementSite.each_context` supplies the presentation-only `management_ui`
  flag. No queryset or permission logic changed.
- `portal/static/portal/management.css` scopes styling to `.management-ui`.
- `management/navigation.html` uses Django's permission-filtered `available_apps`
  and existing service-access context. Staff-account links remain superuser-only.
- The overview reuses existing `cards`, `app_list` and `recent_actions`.
- Service search field names, GET behavior, table values and pagination links
  remain intact. The table wrapper gains an accessible region label and keyboard
  focus for scrolling.

## Validation

Local execution uses the existing Django 6.1.1 test dependencies with temporary
SQLite and no production `.env` or credentials. No external provider was called.

- Full Django suite: **192 passed** (188 existing plus 4 presentation-boundary
  tests). System checks passed; no model migration changes detected.
- JavaScript provisioning tests: **9 passed**.
- New tests cover restricted record navigation, Management logout/CSRF, login
  form preservation, and absence of the theme on customer/legacy-admin pages.
- Browser checks use Chromium with a disposable SQLite fixture and requests
  restricted to the local test server. Synthetic names, addresses and records are
  local test data only and are not included in the application or deployment.
- Ten Management views rendered at 1440, 1024, 768 and 390px: overview, orders,
  order detail, VPS services, staff list/add/edit, plans/add and password change.
  Login and three restricted/no-permission staff overviews were also captured.
- All 40 main browser checks returned HTTP 200 with no page overflow or script
  errors. Desktop/mobile screenshots were inspected; phone header overlap and
  inherited link/close-button styles were corrected.
- Axe WCAG A/AA checks on the ten views at desktop and phone widths found no
  contrast violations. The staff-permission edit widget has two prohibited-ARIA
  findings at each width, generated by the bundled Django SelectFilter2 search
  tooltip spans (not new application markup). They remain documented rather
  than changing the framework's permission widget. This is not a real screen
  reader test or a claim of full accessibility compliance.

These checks do not establish live PostgreSQL behavior, real assistive-technology
usability, other browser rendering, or infrastructure/payment behavior. None of
those live actions are needed to review this presentation change.

## Preview and deployment boundary

Nothing in this task is deployed. Use the existing isolated preview, with its
test database and integration credentials disabled, to review the branch before
any production change. Check administrator and restricted-staff views separately.
Retain both access and form validation checks; appearance does not grant access.

No model or schema migration is introduced. A future deployment requires the
template directory, new stylesheet, static collection, Django checks and the
usual separately authorized service restart. A code rollback to the preceding
compatible deployment needs no database reversal; recorded business/staff edits
must be retained. This document is not authorization to deploy or restart.
